# ai-conversation-search 利用フィードバック対応

## Context

実利用中の AI エージェントから使用感フィードバックが届いた。検索本体（trigram FTS + bm25 + `context_snippet`）は実用的だという評価だが、以下 3 点で調査動線が壊れていた。すべてコードと実 DB で再現を確認済み。

1. **`tree` が実質使えない** — ノードの `summary` が全件空。「セッションを俯瞰してから深掘りする」という設計上の動線が塞がり、キーワード検索の打ち直しに追い込まれた。SKILL.md が手動 `grep` を強く禁じている以上、`tree` が死ぬと代替手段がない
2. **`--limit` 既定 20 の無言打ち切り** — 全検索が黙って上位 20 件で切られていたことに利用者は最後まで気づかなかった。「ヒットしなかった＝存在しない」と誤診する危険がある
3. **observer セッションのノイズ** — claude-mem の observer が一次セッションのツール実行を丸ごと複製するため、実ヒット 1 件に影が 3〜5 件付く

加えて `tree` に短縮 ID を渡すと `not found` になる点（git の prefix 感覚とのギャップ）と、SKILL.md に `--content` / `--limit` の記載が一切ない点（利用者がフラグを見落とした直接の原因）も是正する。

## Step 1: tree の summary を読み出し時に補完する

**変更**: `src/search.rs:1372`

```rust
// 変更前

// 変更後
summary: msg
    .summary
    .clone()
    .filter(|s| !s.trim().is_empty())
    .or_else(|| Some(summary_from_content(&msg.full_content))),
```

`MessageRow.summary` は `Option<String>`、`full_content` は `String`（`src/search.rs:139-140`）、`summary_from_content(&str) -> String` なので型は合う。

**注意**: human 出力の `print_tree_nodes` は summary をさらに 80 文字に切る（`src/cli.rs:1000`）。120 文字全部が見えるのは `--json` のみ。手動確認のときに「120 文字出ていない」と誤判定しないこと。

## Step 2: tree が短縮セッション ID を受け付ける

`get_conversation_tree`（`src/search.rs:1160`）の冒頭で ID を解決する。**エラーは既存契約どおり in-band**（`Ok(ConversationTree { error: Some(...) })`）で返す。`Err` にすると `src/main.rs:16-19` 経由で `exit(1)` になり、`--json` 消費側の契約が壊れ、既存テスト `src/search.rs:3822-3823`（`result.error.unwrap().contains("not found")`）も落ちる。

**変更**: `src/search.rs` に解決関数を追加する。戻り値は `Result<Option<String>>` とし、「解決できなかった／曖昧」は `Ok(None)` + 呼び出し側で in-band エラー生成、という形にはせず、`Result<std::result::Result<String, String>>`（内側 `Err` がユーザー向けメッセージ）のような素直な形にする。実装時に既存のエラー表現に寄せて決める。

```rust
use rusqlite::OptionalExtension;  // src/search.rs:4 は Connection しか import していないので追加が必要

/// 完全一致を優先し、なければ一意な前方一致で解決する。
/// 曖昧なときは候補数を含むメッセージを返す（黙って 1 件選ばない）。
fn resolve_session_id(conn: &Connection, input: &str) -> Result<std::result::Result<String, String>> {
    let exact: Option<String> = conn
        .query_row(
            "SELECT session_id FROM conversations WHERE session_id = ?",
            [input],
            |r| r.get(0),
        )
        .optional()?;
    if let Some(id) = exact {
        return Ok(Ok(id));
    }

    // OpenCode / Codex は DB 上 `oc:` / `codex:` プレフィックス付き
    // (src/indexer/opencode.rs:10, src/indexer/codex.rs:10)。素の UUID を渡されても
    // 引けるよう 3 パターン試す。両側 `%` は使わない — UUID の一部が中間一致する事故を防ぐ。
    let esc = escape_like(input);
    let mut stmt = conn.prepare(
        "SELECT session_id FROM conversations
         WHERE session_id LIKE ?1 ESCAPE '\\'
            OR session_id LIKE ?2 ESCAPE '\\'
            OR session_id LIKE ?3 ESCAPE '\\'
         LIMIT 11",
    )?;
    let matches: Vec<String> = stmt
        .query_map(
            [format!("{esc}%"), format!("oc:{esc}%"), format!("codex:{esc}%")],
            |r| r.get(0),
        )?
        .collect::<std::result::Result<_, _>>()?;

    match matches.len() {
        0 => Ok(Err(format!("Conversation {} not found", input))),
        1 => Ok(Ok(matches.into_iter().next().unwrap())),
        n => Ok(Err(format!(
            "Ambiguous session id '{}' matches {} conversations: {}",
            input, n,
            matches.iter().take(3).cloned().collect::<Vec<_>>().join(", ")
        ))),
    }
}
```

`escape_like`（`src/search.rs:239-244`）を再利用する。`LIMIT 11` は「10 件超」を判別しつつ全件走査を避けるため。

`get_conversation_tree` は解決後の ID で既存の 2 クエリ（`src/search.rs:1162`, `1168`）を回す。エラーメッセージには**利用者が渡した文字列**を出す（何を渡したか分かるように）。

**テスト**

- `test_tree_resolves_unique_prefix` — 8 文字の先頭一致でツリーが引けること
- `test_tree_ambiguous_prefix_returns_inband_error` — 同一 prefix の会話 2 件で、`Err` ではなく `result.error` に件数入りメッセージが入り、`tree` が空であること
- `test_tree_exact_match_wins_over_prefix` — 完全一致 ID が別 ID の prefix になっている場合に完全一致が選ばれること
- `test_tree_resolves_prefixed_source_id` — 素の UUID から `oc:` / `codex:` 付き ID に解決できること
- 既存 `src/search.rs:3822-3823` の not-found テストが通り続けること（回帰）

## Step 3: `--limit` 打ち切りを常時通知する

JSON の出力形状（裸配列）は変えない。既存の消費側（`bin/ai-conversation-search` ラッパー、`pick`、スキル記述）を壊さないため。**打ち切りの有無を判定して stderr に常時出す**。

**4 経路すべてを塞ぐ**（1 つでも漏らすと Context 問題 #2 が半分残る）:

| 経路 | 場所 | 判定方法 |
|---|---|---|
| FTS 非 grouped | `src/search.rs:716-786` | `truncate` 直前の `all_results.len() > limit`。早期停止（`src/search.rs:761-763`）が「ちょうど limit 件」で止まった場合に備え、break 直前にフラグを立て `broke_early && len == limit` も打ち切り扱い |
| FTS grouped | `src/search.rs:940-969` | 早期停止がなく全バッチを処理するため、`order.truncate(limit_usize)` 直前の `order.len() > limit_usize` が厳密 |
| LIKE-only 非 grouped | `src/search.rs:679-687` | SQL を `LIMIT ?` → `limit + 1` にし、1 件多ければ捨てて `truncated = true` |
| LIKE-only grouped | `src/search.rs:864-877` | 同上 |

`broke_early && len == limit` の判定は「残り候補が全部フィルタで落ちる」場合に過剰警告になりうるが、見落とし（偽陰性）は出ない。取りこぼすより過剰に警告するほうが今回の目的に合う — この理由をコードコメントに残す。

**`limit < 0` の扱い（先に潰す）**: `search_conversations` には `limit < 0` のバリデーションがない（grouped 側には `src/search.rs:823-828` にある）。現状 `limit as usize` が `usize::MAX` になり `truncate` は無害な no-op だが、`limit + 1` を書くとデバッグビルドでオーバーフロー panic する。**grouped と同じバリデーションを `search_conversations` に足す**（`saturating_add` で誤魔化さない — 負の limit は入力エラーとして扱うのが正しい）。

**`SearchStats` の変更**: `truncated: bool` を追加する（`src/search.rs:209`）。`SearchStats` は `gather_search_stats`（`src/search.rs:611-641`）でのみ構築され、呼び出しは 6 箇所（`:685, :703, :794, :875, :889, :983`）。全箇所の署名変更が必要。`list` 経路は自身の SQL cap があるが今回は対象外とし、常に `truncated: false` を返す（`list` の打ち切り通知は tech debt に記録）。

**出力**: `src/cli.rs` の human 分岐（`:738-742`）と JSON 分岐（`:706-709`）の両方で、`truncated` なら `--verbose` の有無にかかわらず stderr に 1 行:

```
Note: showing first 20 results (more matches exist). Raise with --limit.
```

grouped 側（`src/cli.rs:806-816`, `838-842`）も同文（"sessions"）で対応する。

**`stats.matched_messages` の意味は変えない**（`src/search.rs:926-930` に記載された grouped との差異はそのまま）。真の総数を出すには追加 COUNT が必要で early-stop の利点を失うため、「もっとある」という事実だけを正確に伝える。この判断理由をコードコメントに残す。

**テスト**

- `test_search_reports_truncation_when_more_results_exist` — 5 件マッチで `limit=3`、返却 3 件かつ `stats.truncated == true`
- `test_search_no_truncation_flag_when_within_limit` — 3 件マッチ・`limit=10` で `false`
- `test_search_truncation_boundary_exact_limit` — マッチ数 == limit で `false`（境界で誤警告しない）
- `test_grouped_search_reports_truncation`
- `test_like_only_search_reports_truncation` — 全語 2 文字のクエリ（LIKE-only 経路）でも打ち切りが検出されること
- `test_search_negative_limit_is_rejected` — 非 grouped でも `limit < 0` がエラーになること

既存テストの `BATCH_SIZE` 前提（`src/search.rs:1722`, `1791`, `3475` が 500 件超のフィクスチャを使う）を壊していないか確認する。

## Step 4: observer セッションをインデックス時にスキップする

### 4-0. 検出は 2 段構え（パスで弾き、マーカーで確認）

実測で **path ベースとマーカーベースの検出集合は完全一致**（双方向で差分 0）。observer は単一のプロジェクトディレクトリ `~/.claude/projects/-Users-yoshiki-kadono--claude-mem-observer-sessions` 由来で、DB 上の `project_path` は 2 表記（`…/.claude-mem/observer-sessions` 20,364 件、ダッシュ復号フォールバックの `…//claude/mem/observer/sessions` 1,492 件）。

- **スキャン段階でディレクトリごと除外する**（`discover_project_dirs`, `src/indexer/claude_code.rs:349-400` の結果から落とす）。約 2 万ファイル・747MB の JSONL をパースせずに済む
- **マーカー判定（4-1）は保険として残す**。claude-mem がディレクトリ構成を変えたときや `CONVERSATION_SEARCH_EXTRA_DIRS` 経由で入ってきた場合に効く

### 4-1. 検出関数

`src/summarization.rs` の `is_summarizer_conversation`（`src/summarization.rs:127-151`）の隣に追加する。`crate::indexer::Message` のフィールドは `content`（`src/indexer/mod.rs:40`）。

```rust
/// claude-mem の observer セッションか判定する。
/// observer は一次セッションのツール実行を XML でミラーするだけで、会話としての
/// 一次情報を持たない（発言も推論も一次セッション側に残り、observer 自身の観測ログは
/// ~/.claude-mem/claude-mem.db に別途保存される）。
pub fn is_observer_conversation(messages: &[crate::indexer::Message]) -> bool {
    let first_user = match messages.iter().find(|m| m.message_type == "user") {
        Some(m) => m,
        None => return false,
    };
    // 本文中に含まれるだけの会話（observer の XML を話題にしているセッション）を
    // 拾わないよう、先頭の user メッセージだけを見る。
    first_user.content.contains("<observed_from_primary_session>")
}
```


既存の sync_state 書き込みは `src/indexer/claude_code.rs:1109` と `:1233` にあり、どちらも `unchecked_transaction()`（`:1067`）より後の `tx.execute` である。スキップ位置（`:961`）はトランザクション開始前なので `self.conn.execute` を直接使う（単一文なので atomic）。executor が違うため共通ヘルパには切り出さず、3 箇所目としてインラインに書き、既存箇所への参照コメントを残す。

既存 observer ファイルは sync_state に行を持つため `:926` の mtime チェックで既にスキップされる。問題は**新規に生成されるファイル**なので、この記録が必要。

### 4-3. 復旧レバー

環境変数 `CONVERSATION_SEARCH_INDEX_OBSERVER=1` でスキップを無効化する。既存の `CONVERSATION_SEARCH_EXTRA_DIRS`（`src/indexer/claude_code.rs:397`）と同じ env 方式にする。

**ただし env だけでは復旧しない**。`--all` は日付窓を広げるだけで（`src/cli.rs:510`）、mtime スキップ（`src/indexer/claude_code.rs:924-937`）は効いたままなので、4-2 で sync_state を記録した observer ファイルは 1 件も再取り込みされない。`index` に `--force` フラグを追加し、指定時は mtime チェックを丸ごと飛ばすようにする（`--all` の既存意味は変えない — 全件再パースは重く、既定挙動を変えると通常運用が遅くなる）。

復旧手順は `CONVERSATION_SEARCH_INDEX_OBSERVER=1 ai-conversation-search index --all --force` となる。

### 4-4. 前提: FTS の DELETE トリガを先に直す（Step 0 相当・必須）

**この修正なしに 236,341 行を削除してはいけない。** 同数の孤児 FTS エントリが残り、bm25 の文書長正規化と IDF が歪む。`query_fts_rowids`（`src/search.rs:1036-1048`）は rowid と bm25 しか読まないためエラーにならず、**検索品質が静かに劣化する**（`src/search.rs:1062` の自動 rebuild も発火しない）。

`data/schema.sql:64-72` の 2 トリガを外部コンテンツ FTS5 の正しい形に直す:

```sql
CREATE TRIGGER IF NOT EXISTS messages_ad AFTER DELETE ON messages BEGIN
    INSERT INTO message_content_fts(message_content_fts, rowid, message_uuid, full_content)
    VALUES ('delete', old.rowid, old.message_uuid, old.full_content);
END;

CREATE TRIGGER IF NOT EXISTS messages_au AFTER UPDATE ON messages BEGIN
    INSERT INTO message_content_fts(message_content_fts, rowid, message_uuid, full_content)
    VALUES ('delete', old.rowid, old.message_uuid, old.full_content);
    INSERT INTO message_content_fts(rowid, message_uuid, full_content)
    VALUES (new.rowid, new.message_uuid, new.full_content);
END;
```

`init_schema` の第 2 パス（`src/schema.rs:110`）が `SCHEMA_SQL` を再実行するが、`CREATE TRIGGER IF NOT EXISTS` は既存トリガを置き換えないため、**マイグレーションで明示的に `DROP TRIGGER` してから作り直す**必要がある（`src/schema.rs:319-321` に既存の DROP パターンがある）。これは非破壊なので通常のマイグレーション（version 9, `MigrationKind::Sql` または `Custom`）で行ってよい。`MigrationKind::Custom` にする場合は `run_custom_migration`（`src/schema.rs:288-293`）と `detect_custom_migration_applied`（`src/schema.rs:194-210`）の**両方**に version 9 のアームを足すこと（未知バージョンで `unreachable!()` し、後者は新規 DB の `bootstrap_existing_db` からも呼ばれるため panic する）。

既存の孤児エントリは `prune-observer` 実行時の `rebuild` でまとめて解消する（下記）。

**テスト**（`src/schema.rs` の `mod tests`, `:363`）: `test_fts_delete_trigger_removes_index_entry` — メッセージを 1 件入れて `MATCH` でヒットすることを確認 → 削除 → `MATCH` でヒットしなくなること。現行トリガでは落ち、修正後に通る。

### 4-5. 既存行の掃除は「明示サブコマンド」で行う（マイグレーションにしない）

**マイグレーションにしてはいけない理由**: `search` は `maybe_background_index()`（`src/cli.rs:276`, 呼び出しは `:694`）でデタッチしたインデクサを起動し、そこで `init_schema` が走る。マイグレーションに載せると、アップグレード後の最初の検索で**236,341 行の DELETE がバックグラウンドで無言かつ不可逆に走る**。利用者がバックアップを取る前に消える。加えて `run_custom_migration`（`src/schema.rs:288-293`）と `detect_custom_migration_applied`（`src/schema.rs:194-210`）は未知バージョンで `unreachable!()` するため、後者は新規 DB の `bootstrap_existing_db` からも呼ばれ panic する。

**採る形**: 新サブコマンド `prune-observer` を追加する。

- `src/cli.rs` の `Commands` に `PruneObserver { dry_run: bool, quiet: bool }` を足し、`src/cli.rs:411` 付近のディスパッチに追加
- 書き込み接続（`db::connect(path, false)`）を開き、単一トランザクションで実行
- `--dry-run` で削除対象件数だけ表示（既定は実削除だが、実行前に件数と所要時間の目安を stderr に出す）
- 進捗・完了メッセージは `eprintln!` を使う。`log::info!` は `src/main.rs:14` が素の `env_logger::init()` なので既定レベル Error で出ない

```sql
-- 単一トランザクション内
CREATE TEMP TABLE observer_sessions AS
SELECT session_id FROM (
  SELECT session_id, full_content,
         ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY timestamp ASC) rn
  FROM messages WHERE message_type = 'user'
) WHERE rn = 1 AND full_content LIKE '%<observed_from_primary_session>%';

DELETE FROM conversations WHERE session_id IN (SELECT session_id FROM observer_sessions);
DELETE FROM messages      WHERE session_id IN (SELECT session_id FROM observer_sessions);
DROP TABLE observer_sessions;
```

**session_id を先に確定させてから両テーブルに適用する**こと。`DELETE FROM conversations WHERE session_id NOT IN (SELECT session_id FROM messages)` のような孤児掃除形にしてはいけない — raw fallback（`src/search.rs:1183-1186`, `1199`）は「conversations 行はあるが messages が 0 件」を前提とする正規の機能で、将来そうした行を巻き添えにする。逆に conversations を残して messages だけ消すのも不可で、`cmd_index` が毎回呼ぶ `repair_orphan_conversations`（`src/indexer/claude_code.rs:1275-1289`）が毎回無駄な復活処理を走らせる。

**削除後に FTS を必ず再構築する**（同一トランザクション内、DELETE の後）:

```sql
INSERT INTO message_content_fts(message_content_fts) VALUES('rebuild');
```

4-4 でトリガを直しても、**それ以前に蓄積した孤児エントリは残る**ため rebuild が要る。既存の同パターン: `src/schema.rs:352`（migration 8）、`src/search.rs:1668`（repair 経路）。rebuild は 57 万行の再索引になるので、これが `prune-observer` の所要時間の主成分になる見込み。

- **所要時間は実装時に実測する**: 検出 SELECT 単体で実 DB（4.2GB / 808k 行）15 秒。236,341 行の DELETE と trigram FTS の削除が加わる分は未測定。**バックアップコピーに対して先に実行して実測し、その値を `--dry-run` の見積もり表示に埋める**
- `VACUUM` は行わない（4.2GB の DB で長時間ロックするため）。ファイルサイズは縮まないが空きページは再利用される
- `claude_code_sync_state` のエントリは残す。スキップ対象なので再読み込みは不要。`CONVERSATION_SEARCH_INDEX_OBSERVER=1` で取り込み直す場合は `index --all` が必要な旨をドキュメントに書く

### 4-6. 2 つの検出器の一致を検証する

実行時の判定（4-1、パース済み JSONL の順序で最初の user メッセージ）と `prune-observer` の SQL 判定（DB 上の timestamp 最小の user 行）は別物で、インデクサは挿入前に行をフィルタする（`src/indexer/claude_code.rs:1079-1160`）。実測した 100% / 誤検知 0 は **SQL 版で測った値**であり、実行時版は未検証。

対策: 同一フィクスチャ（実 observer JSONL を 1 本コピーしたもの）に対して両方を走らせ、判定が一致することを確認するテストを置く。
